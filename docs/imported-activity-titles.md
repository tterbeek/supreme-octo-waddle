# Imported activity titles

Shared naming service:
`supabase/functions/_shared/importedActivityTitle.ts`.
Polar and the existing, still-paused Strava importer both use it; future provider
adapters can pass the same normalized input. No AI call is involved.

## Naming

Only empty or complete generic source titles are replaced. Matching is
case-insensitive, tolerates underscores/hyphens and whitespace, and recognises
the mapped sport's common names plus provider sport-catalog aliases. Custom
titles such as “Run with Sam”, “Morning Run”, or “Race day!” are preserved.
There is no reliable way to detect every provider's autogenerated sentence;
unrecognised titles are conservatively retained.

Generated titles use the local start hour and MoveNotes activity label:

| Local time | Prefix |
| --- | --- |
| 00:00–03:59 | Night |
| 04:00–06:59 | Early morning |
| 07:00–11:59 | Morning |
| 12:00–13:59 | Lunchtime |
| 14:00–16:59 | Afternoon |
| 17:00–23:59 | Evening |

Real instants use a supplied IANA zone (including daylight-saving rules) or UTC
offset. A provider-local datetime without a zone is already wall-clock local
time and is not converted a second time. Without separate zone information,
the datetime's encoded wall time/offset is retained; the server's local timezone
is never used. An invalid/missing start produces only the activity label rather
than an invented time bucket.

Polar's local start and UTC-offset minutes are also used to store the correct
`started_at` instant. Strava's special `start_date_local` representation is
adapted to a local wall-clock before calling the shared service. Provider
schemas: [Polar v4](https://www.polar.com/polar-api-v4/) and
[Strava dates](https://developers.strava.com/docs/#dates).

## Optional approximate starting locality

The activity is inserted with a complete time/type title immediately. Optional
route fetching and geocoding run afterward via
[Supabase background tasks](https://supabase.com/docs/guides/functions/background-tasks),
with at most three jobs active at once. There is no geocoding dependency in
the insertion or sync response path.

- Choose a coordinate approximately 150 m along the track, interpolating sparse
  segments. A 100–150 m track can use its last valid point. Reject invalid points
  and tracks that do not get at least 100 m away from the start, including short
  loops returning home. A single start coordinate is **not** a fallback.
- Use the existing server-side `GOOGLE_MAPS_API_KEY`, with a five-second geocode
  timeout. Request locality/postal-town/municipal administrative result types;
  extract only typed address components. Never use a formatted street address,
  neighbourhood, park/POI, state or country as the title suffix. See
  [Google reverse-geocoding result types](https://developers.google.com/maps/documentation/geocoding/guides-v3/requests-reverse-geocoding).
- Reuse `location_cache` under an `import-locality:` namespace so old park/POI
  results cannot be mistaken for towns. Cache only the coarse point (three
  decimal places) and locality, not a GPS track or exact home/start location.
- Missing GPS, missing key, no sensible locality, provider/geocoding failures,
  and interrupted workers leave the usable time/type title intact. Background
  work is best-effort within the platform runtime limit, not a new durable queue.
- New Polar imports fetch route features in separate one-day requests, grouped
  by local date. Strava detail fetching/polyline decoding also happens only
  after insertion, only for generic titles. No raw coordinates, routes, provider
  titles or API keys are logged by the new naming path.

Successful enrichment updates only `title`, using an atomic compare-and-set on
the inserted row's ID, owner, provider/external ID, original title, type, start
instant, note-update timestamp and enrichment status. Editing/handling/deleting
the activity meanwhile prevents a stale background update. The import identity,
activity values, notes and existing deduplication rules are unchanged. Retried
imports do not overwrite existing titles; there is no bulk rename/backfill.
The added locality appears on the next normal feed fetch/refresh.

## Deployment and verification

No database migration, frontend deployment, new public endpoint or new secret
is required. Deploy the two existing import functions to use their new shared
helpers. Strava remains paused in the app; deploying its updated code does not
enable the integration. If the Google key/API is not configured, time/type
titles still work with no locality.

```bash
npx supabase functions deploy polar-import-activities --project-ref ljthydvstmbcgqdnqkvx --use-api
npx supabase functions deploy strava-import-activities --project-ref ljthydvstmbcgqdnqkvx --use-api
```

Focused tests cover all bucket boundaries, IANA/DST/offset/local timestamps,
custom-title preservation, multiple providers/types, GPS offset selection,
address rejection, cache separation, geocoding fallback, nonblocking/bounded
background execution, and concurrent edit/ownership guards. Provider/geocoder
calls in tests are fictional. Actual Polar route access, Google billing/key
configuration, geographic accuracy and production worker completion are not
verified by the unit/bundle checks. Nothing deploys automatically.
